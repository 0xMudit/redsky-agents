# Design: Red Sky Beta — distribution-first wedge

Generated by /office-hours on 2026-10-11

Mode: Startup (pre-product)

## Problem Statement

A feature-complete local AI teammate app (v0.2.0: agents, memory, schedules,
Auto Review, workspace sandbox, rooms, notifications, search) exists with zero
public distribution. The only way to run it is `git clone && npm install &&
npm start`. Nobody who owes the founder nothing can try it in under ~10 minutes
without an engineering setup. Three weeks after open-source, the public record
is 0 stars, 2 forks, 1 external issue — no stranger has felt the product.

The beta's job is not more features. It is making the thing people can actually
install, and instrumenting a behavioral signal that demand is real.

## Demand Evidence

Unproven. No stranger has been named. The strong bucket ("strangers are using
it") did not survive a names-and-behavior push; the closest named user is the
founder himself. Everything in this plan treats demand as a hypothesis to be
tested by behavior (install → first task → return), not by stars or "looks cool."

## Status Quo

Manual agent juggling: separate terminals, re-prompting a CLI agent day after
day, context re-pasted, nothing runs on a schedule without the human. Cost is
less money than attention — five-minute re-frictions that add up to
"my agents forget who I am." Red Sky's wedge displaces that, not SaaS.

## Target User & Narrowest Wedge

The founder, first: a solo technical builder running multiple local agents,
privacy-forward, no account, one machine. Beta ships for that seat, knowingly
(own-dogfood risk accepted; the wedge is validated by recruiting strangers who
fit the same seat).

Wedge: **persistent local teammates that remember and run on a schedule**.
The one loop that must shine in the beta:

create agent → give it a job → teach a routine → walk away → notification
comes back with a result and a workspace diff.

## Constraints

- Local-first is non-negotiable: no backend, no accounts, no telemetry. The
  privacy promise is the differentiator, so the demand instrument must respect
  it (feedback = outbound GitHub issue, not silent phone-home).
- Build on the existing v0.2.0 code; no rewrite. The delta is distribution,
  onboarding, and sharpening that one loop.
- OpenCode CLI + a configured provider remain the runtime requirement.

## Premises (working assumptions — gate dismissed, adopted as defaults)

1. Demand is unproven; beta succeeds by making strangers feel loss by behavior.
2. Wedge is persistence + schedule + memory vs. manual terminal juggling.
3. Beta persona == the founder's seat (solo technical builder, one machine).
4. Local-first constraint holds through the beta.
5. Distribution, not features, is the current blocker.

## Approaches Considered

### Approach A: Distribution-first beta (chosen)
Add packaging (`electron-builder`), a release CI workflow that attaches signed-
or-unsigned installers on tag, an in-app first-run guide that detects OpenCode
presence and walks provider auth, and a privacy-safe feedback path (button →
prefilled GitHub issue with a redacted log bundle). Feature surface stays v0.2.0.
Effort: M. Risk: Low-Med (signing).

### Approach B: Wedge-first sharpening
Skip installers; polish the schedule/notification loop and ship as a zip/portable
build. Rejected: it defers the #1 proven blocker (nobody can even run it
without a build toolchain), and releases the least differentiated thing while
the loop work takes weeks.

### Approach C: Channel-first (lateral)
No binaries at all — a "claim your first teammate in 3 minutes" runbook plus
a demo video, distributed to r/selfhosted / HN, measuring who completes setup.
Rejected as the primary path: it trains drive-by installs on, which evaporate
without a real binary and a real first-run experience; kept as the *announcement*
half of A's go-to-market.

## Recommended Approach

A — distribution first, instrumented for behavior:

1. **Packaging.** Add `electron-builder`, an app icon, and win/mac/linux targets
   (NSIS, dmg, AppImage/deb). Electron is already `^37`; config lives in
   `electron-builder.yml`. Unsigned dev builds are acceptable for the beta — the
   OS will warn on first launch (README already documents this).
2. **Release pipeline.** Tag-triggered GitHub Actions job: build → package →
   upload to a GitHub Release. `v0.3.0-beta` is the first ship.
3. **First-run onboarding.** In-app detection of `opencode` on PATH; if missing,
   guide install + `opencode auth`; then template picker → first task. Mirrors
   the README checklist so a stranger doesn't touch a terminal.
4. **Behavior instrument (privacy-safe).** One "beta feedback" control that
   opens a prefilled GitHub issue: task title, count of tasks run, count of
   routines created, app + OpenCode versions, redacted tail of `logs/app.ndjson`.
   No phone-home; the user chooses to send. This is the demand log.
5. **Ship + announce.** Tag, release, then one post to r/selfhosted and one to
   HN (Show HN) + a 90-second screencap. Link straight to the release page.

## Success Criteria (behavioral, 2 weeks post-ship)

- ≥ 25 strangers install and complete their first task (issue/template flow).
- ≥ 5 return to create a scheduled routine ("teach a routine") — the wedge loop.
- ≥ 5 distinct feedback issues or opened issues from non-contributors.
- Installer completes on all three OSes without the founder's help.

If 10 strangers feel loss (panic on a bot error, ask when the next feature
ships, schedule a routine on a second bot), demand is real and the revenue
question gets attacked next. If the beta is crickets, the honest read is that
the wedge or the seat is wrong — cheaper to learn now than after more features.

## The Assignment

Ship the `v0.3.0-beta` installer to three channels by end of week and get
**ten strangers** to the point where one of them would feel loss if a bot
forgot them. Not "go build it" — a dated, countable target: 10 installers
completed, 5 routines created, 5 issues filed.

## What I noticed about how you think

- You dismissed the premise gate with "let's start building, stop asking Qs."
  That's agency, and it's also the exact pattern that ships un-validated
  features. The doc keeps the five premises so you sign them later, cheaply.
- You called the deliverable a "beta version" of what already exists rather than
  an MVP rewrite — that instinct (find the existing 80%, sharpen the missing
  20%) is the right reuse-first reflex and it's the cheapest good plan here.
- The one answer you could not give was a stranger's name. Watch that hole:
  Red Sky currently runs on conviction and a beautiful README. The beta's
  feedback channel is built to fill it with facts.
